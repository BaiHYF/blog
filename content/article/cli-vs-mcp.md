> 摘要：2024 年底 Anthropic 发布 Model Context Protocol（MCP）之后，关于“AI Agent 应该通过什么接口调用外部工具”的讨论迅速升温，到 2026 年演化为一场持久的工程争论。本文以命令行接口（CLI）与 MCP 为对象，先澄清二者在概念上分属不同层级，再从执行环境、成本、可靠性、能力发现、授权与审计、状态管理、生态分发等维度逐一比较，随后用可复现的基准数据检验“CLI 更便宜、MCP 更可靠”这类判断成立的前提，最后结合飞书、Notion 等产品同时提供两种接口的实践，说明争论的实质不是取舍而是分工。结论是：CLI 与 MCP 分别适合本地单用户与远程多租户两类场景，二者可以组合使用；随着以 Skill 为代表的上层抽象逐渐成熟，“用哪个协议”这个问题的重要性在下降。

## 一、引言

如果一个 AI Agent 需要访问外部世界的某种能力，产品设计者首先要回答一个不算新但如今绕不开的问题：把这种能力暴露成什么样的接口？是让人和模型都能直接敲的命令行工具，还是一套可供模型在运行时发现、调用并受控授权的结构化协议？

这两种做法在过去两年里各自积累了一批支持者，也各自催生了一批产品。Model Context Protocol 由 Anthropic 于 2024 年 11 月发布，目标是让“模型调用工具”这件事标准化，一度被称为 “USB-C of AI”。与此同时，Git、Docker 这类命令行工具已经存在了几十年，模型在训练数据里见过它们无数次，使用成本几乎为零。到 2026 年，关于两者优劣的讨论从技术社区蔓延到创业圈。有人在 Reddit 上引用基准数据发问：MCP 比 CLI 多消耗几十倍 token，成功率反而更低，为什么大家还在造 MCP server，是不是只因为它有一个听起来很好的名字。

争论本身说明不了输赢，但它值得被认真梳理。原因有两条。其一，结论高度依赖前提：本文后面会看到，几乎所有“CLI 更好”或“MCP 更好”的说法，都需要限定场景才成立。其二，争论的双方常常在比较两个并不属于同一层级的东西：CLI 是一种程序形态，MCP 是一套协议。把两者放在一起，真正的问题其实是：在 Agent 时代，模型连接外部世界的主要入口应该长什么样。

本文的安排如下。第二节先厘清 CLI 与 MCP 分别是什么，以及一个常被忽视的区分：传统 CLI 与为 Agent 新做的 CLI 并不共享同样的优势。第三节解释为什么这两个概念会被放在一起比较。第四节从十个维度做逐项比较。第五节用可复现的基准数据检验常见说法的边界。第六节和第七节分别总结 CLI 与 MCP 的主场和代价。第八节考察厂商的实际做法。第九节归纳争论背后的真实分界线。第十节做一点展望。第十一节给出结论。

## 二、CLI 与 MCP：先分清它们是什么

这一节先各自给出定义，再指出两个容易混淆的点。

### 2.1 CLI：命令行，一种程序形态

CLI 是 Command Line Interface 的缩写，指通过输入命令而非操作图形界面来使用计算机的一类程序。git、docker、aws、scp 都属于 CLI。它的构成很简单：一个可执行程序加上若干参数，结果通过标准输出、标准错误和退出码返回。几十年间，这些工具的用法沉淀在海量的文档、教程和公开代码里，成为开发者日常的一部分。

Unix 的设计哲学可以概括为几句话：一个工具只做一件事，文本是通用接口，管道把若干工具串成一条流水线。这三句话对后文理解 CLI 的优势很重要，值得记住。

### 2.2 MCP：模型上下文协议，一套集成契约

MCP 是 Model Context Protocol 的缩写，由 Anthropic 在 2024 年底发布，是一套开放协议。它规定模型（或承载模型的宿主程序）如何发现并调用外部工具：能力被组织成带输入输出结构描述的工具（Tool），可读取的数据源称为资源（Resource），可复用的提示模板称为 Prompt；通信采用 JSON-RPC 2.0，传输方式分本地 stdio 与远程 Streamable HTTP 两种。

用飞书的例子可以直观看到两种接口形态的差别。同一个“查今天的日程”动作，CLI 呈现为一组给人看的帮助文本，模型需要自己推断某条子命令做什么、参数怎么传；MCP 呈现为一个结构化工具定义，字段、类型、格式都写清楚，模型照着填即可。前者像给模型一本操作手册，后者像给模型一张填空表格。

### 2.3 两个易混点

第一个易混点是 MCP 内部其实可以拆成三层，价值分布并不均匀。协议层定义调用方式，这一层实现起来并不难，工具调用本身早在 MCP 之前就有（Anthropic 的 Tool Use、OpenAI 的 Function Calling）。真正对产品方有价值的是另外两层：运维标准让一个服务按统一约定被连接、调用和维护，省去为每个客户端单独适配；生态分发让用户在平台目录里更容易发现并安装这个服务。需要强调的是，分发依赖第三方平台，不是协议本身能保证的。图 1 展示这三层。

![图 1 MCP 的三层构成](/blog/blog-resources/cli-vs-mcp/fig-mcp-layers.svg)

*图 1 MCP 的三层构成。协议层解决“怎么调用”，运维标准解决“怎么维护”，生态分发解决“怎么被找到”；后两层的价值高于第一层，且分发依赖平台。*

第二个易混点也是本文反复要用到的一个区分：传统 CLI 与 Agent 原生 CLI 不是一回事。gh、git 这类工具最初是给人用的，输出带彩色高亮、进度条，甚至交互式确认；对模型而言这些设计并不友好，但模型在训练数据里反复见过它们，用起来反而顺手。而飞书 Lark CLI、钉钉 dingtalk-workspace-cli 这类新工具，项目简介里直接写着 “built for humans and AI Agents”，从设计阶段就把模型当作主要用户：默认输出 JSON、错误用结构化编码、附带面向模型的技能说明。两类工具顶着同一个“CLI”的名字，优劣却不共享。下文凡不特别说明的 CLI，指的就是后一种，即产品方自己新做的 Agent 原生 CLI。

这两点合起来构成一个判断：MCP 与 CLI 并不是二选一的关系，也不是谁天然是默认起点。它们是针对不同场景的两类方案，先看场景，再谈选择。

## 三、为什么这两个不同层级的东西会被放在一起比较

CLI 是程序形态，MCP 是协议，严格说不在一个维度上。拿它们对比，就像拿 HTTP 与 Bash 对比，类别上并不对等。但在 Agent 的世界里，这两者确实经常被放到同一个问题面前：模型要调用外部能力，接口应该做成什么样子。

原因在于 Agent 与普通软件不同。传统软件的调用方是程序员，接口写清楚，人照着文档调用即可。Agent 的调用方是模型，它会自己决定用什么工具、怎么组合。这带来两个后果。其一，接口的“可发现性”变得重要：模型需要知道有哪些能力可用、参数怎么传，这种信息要么写进模型训练数据（传统 CLI 的路子），要么在运行时通过协议提供（MCP 的路子）。其二，接口的成本结构变得敏感：工具定义、帮助文本都会占用模型的上下文窗口，直接换算成运行成本。

于是问题收敛成一个更实际的表述：模型连接外部世界，靠的是模型已经“会”的命令，还是一套模型可以在运行时“学”的协议。前者的代表是 CLI，后者的代表是 MCP。围绕这个选择，效率派和治理派给出了不同的答案：效率派认为模型对命令行有天然先验，应该直接暴露命令，多包一层协议是浪费；治理派认为一旦 Agent 代表的是客户、员工而非开发者本人，协议带来的授权、审计与边界就不可或缺。两种声音都有道理，也各有适用边界，这正是后文要逐条拆开的。

## 四、分维度对比

把两边放到同一张桌子上逐项比较之前，需要先约定一个前提：这里的 CLI 指 Agent 原生 CLI，MCP 指一个按规范实现的 server。两者的背后往往都是同一套产品 OpenAPI，差别在于包装方式——CLI 把 API 包成命令，MCP 把 API 包成一组带结构描述的工具。

下面按四个主题展开。

### 4.1 成本与效率

Token 成本是最常被讨论的一项。CLI 模式下模型拿到的是很薄的一层命令文档，甚至靠训练先验直接用；MCP 模式下，server 暴露的工具及其 schema 会被注册进模型上下文，工具越多、描述越细，占用的 token 越多。因此同样的任务，两者的上下文开销可能差一个数量级。这一维度的结论前提是模型熟悉该命令；对模型陌生的新 CLI，优势会显著缩小，第五节会用数据说明这一点。

执行链路长短是另一项。CLI 的链路是模型到 shell 再到命令，MCP 多一层客户端到服务端的往返。对本地工具而言这层差别在毫秒级，可忽略；对远程服务，MCP 的额外一跳与连接管理会成为可感知的开销。

### 4.2 使用与调试

可组合性上，CLI 继承了 Unix 管道与脚本能力：只要命令稳定、任务可脚本化，Agent 可以生成一段命令一次跑完，不必每步都停下来思考。MCP 没有原生的串联机制，工具各自独立，Agent 逐步调用。不过 CLI 的组合优势有一个隐含条件：任务必须足够确定、可预测，模型才会生成整段脚本。任务一旦复杂、中间充满不确定性，Agent 仍会退回逐步执行，这时优势就不明显了。

可调试性上，CLI 对开发者友好：执行了什么命令、返回了什么、哪一步报错，在终端里看得见，人可以原样复现。MCP 的调用经过协议层，需要专门的调试工具才能看清输入输出。对早期团队这是实在的排障成本。

### 4.3 能力发现、授权与安全

能力发现是 MCP 相对 CLI 的强项。模型连接一个 MCP server 时，能在初始化阶段拿到完整的能力清单，参数与格式都是结构化的。CLI 靠的是 `--help` 逐步探索，从帮助文本推断参数，推断本身就留出错空间。设计良好的 Agent 原生 CLI 可以用更扁平的命令结构、更规整的帮助与结构化错误输出缩小这个差距，但“探索”这个动作省不掉，MCP 把它提前为一次读取。

授权是另一个关键差异。CLI 本身不做鉴权：git push 时“谁有权限、记在谁头上”由服务端判断，CLI 只是带着凭证发请求。这在单人、单机场景没有问题；一旦要区分用户、租户与操作范围，CLI 的凭证继承模型就力不从心。MCP 的授权规范（OAuth 2.1、按用户 scope、可撤销）把授权放在协议层面，配合服务端的审计日志，可以回答“谁在什么时候、基于什么授权、对哪个对象做了什么”。这是治理侧的核心论据。

安全上需要把话说完整。CLI 的灵活性是双刃剑：给了模型 shell，就等于给了它一把瑞士军刀，模型幻觉可能导致破坏性操作或数据泄露。MCP 的工具边界是预先声明的，模型只能调用已暴露的工具，这降低了越界风险。但“有 schema 就安全”是错觉：schema 只约束消息形状，不授予任何业务权限，真正决定安全的是服务端的鉴权与授权实现。

### 4.4 状态、复用与运维

状态管理上，CLI 通常一次调用开一个进程，跑完即退，内存清空，上一次的结果带不到下一次。MCP server 常驻时可以把登录态、连接、中间结果缓存在内存里供多次调用复用。这适合多步复杂流程。需要注意一个细节：MCP 常驻并不等于协议替你管状态。2026-07 的规范明确弱化“协议会话保存状态”的假设，状态、权限、失败恢复的责任仍在服务端。

跨客户端复用上，CLI 只要 Agent 能跑 shell 就通用，一套代码覆盖 Claude Code、Cursor、Codex 等所有终端 Agent。MCP 号称一次实现处处接入，但不同宿主对工具、资源、OAuth、审批确认的支持并不完全一致，接入不同平台仍需逐个验证。“支持 MCP”不等于“所有 Agent 体验一致”。

运维上，CLI 底层是运行了几十年的 shell，规则稳定，需要维护的是命令本身的兼容性。MCP 规范仍在快速演进，服务方要持续跟进版本更新与各宿主的适配。CLI 是稳定的负担，MCP 是变动的负担，两者都要付，只是形态不同。

## 五、数据说话：基准测试的边界

第四节罗列的判断大多停留在经验层面，第五节用一个公开可复现的基准检验其中最重要的两条：CLI 更省、MCP 更可靠。

### 5.1 Scalekit 基准及其结果

Scalekit 在 2026 年 3 月发布了一组基准（代码与数据开源）：同一模型（Claude Sonnet 4）、同一批只读 GitHub 任务，只改变工具的接入方式，分别测裸 CLI、CLI 加约 800 token 的技能文档、以及 GitHub 官方 MCP server 三种形态，共 75 次运行。结果为两种，其一关乎 token，其二关乎成功率。

token 方面，以最简单的“这个仓库用什么语言”为例，CLI 中位数消耗 1365 token，CLI 加技能约 4724，MCP 达到 44026，相差约 32 倍。复杂度相近的任务差距在 4 到 32 倍之间。差距几乎全部来自 schema：GitHub 的 MCP server 暴露 43 个工具，每次调用都把整套工具定义放进上下文，而模型实际只用其中一两个。

成功率方面，CLI 与 CLI 加技能都是 25/25，MCP 是 18/25，约 72%。失败的 7 次全部是 TCP 连接超时，服务端没有在限定时间内响应。按同一定价折算月度成本，1 万次操作的 CLI 约 3.2 美元，MCP 直连约 55.2 美元，MCP 走网关（过滤 schema 后）估计回到约 5 美元。图 3 汇总了这三组数字。

![图 3 Scalekit 基准的三组结果：token 消耗、成功率、月度成本](/blog/blog-resources/cli-vs-mcp/fig-benchmark-data.svg)

### 5.2 数字背后的三个限定

把上面三组数字原样搬进文章容易，搬的时候需要同时带上三个限定。

第一，token 差距是 schema 注入问题，不是协议原罪。43 个工具的描述一次全塞进上下文，属于实现选择。MCP 规范本身已经提供缓解手段：schema 可带缓存时长（ttlMs），server 可做工具过滤，网关可以只下发与当前请求相关的两三个工具。Scalekit 自己测算，网关做 schema 过滤可削减约 90% 的 token。第二，28% 的失败率来自远程连接超时，属于基础设施问题，本地 stdio 形态的 MCP 并不受影响。第三，也是最重要的一点，这个基准测的 gh 是模型训练过的传统 CLI，它的成功不能外推到产品方新做的 Agent 原生 CLI。新 CLI 对模型是知识空白，模型只能靠帮助文本摸索，此时反而可能比有工具清单兜底的 MCP 更容易出错、更费 token。

另外有一组数据可以说明“省 token”与“成功率”未必同向。Smithery 的第三方基准（756 次运行）显示，在 Codex 这类模型上，CLI 加检索的计费 token 低于原生 MCP（约 64916 对 94823），但 MCP 的任务成功率反而更高（91.7% 对 83.3%）。结论是：没有优化的前提下，谁的 token 更省并不确定，取决于工具暴露多少与模型对工具的熟悉度。控制 MCP 的工具数量、提高 CLI 命令的可发现性，比纠结选哪条路线更重要。

## 六、CLI 的主场

对本地、单人、开发或办公高频的使用场景，CLI 通常是最优解。这一节讲它赢在哪，代价是什么。

### 6.1 CLI 赢在哪

其一，模型对命令行有训练先验。git、gh、docker 这类工具在训练语料里出现频率极高，模型知道参数格式、输出含义与报错方式，几乎不需要额外说明。这一条是 CLI 派最核心的论据，但它的适用范围正是上一节强调过的那道分界线：先验属于传统 CLI，不属于产品方新做的 Agent 原生 CLI。

其二，省 token。模型无需在上下文里常驻整本工具说明书，命令本身自带语义，调用成本很低。

其三，可组合。管道、循环、条件判断让一条命令串起原本需要多次往返的步骤。以图像处理为例，选出横版照片、加水印、上传三步，CLI 下可以写成一串管道一次执行，模型只参与生成命令和接收结果两次通信；若用逐步的工具调用，每一步都要等模型思考与往返。

其四，人机同用，可调试。开发者可以在终端原样敲出模型执行过的命令，亲眼复现问题。命令本身成了复现步骤。

其五，认证链路短。gh auth login、aws configure 这类命令装完即用，个人场景下没有额外的授权仪式。

其六，生态现成。几十万个现成 CLI 不用改造，只要 Agent 能跑 shell 就能调用。

### 6.2 CLI 的代价

代价集中在边界上，而不是效率上。

一是对特殊字符和输出的脆弱性。文件名里的单引号、输出里混入的进度条或彩色转义符，都可能导致命令解析失败，而且错误信息往往难以理解。二是无类型管道容易静默失败：对人类而言 grep、jq 的串联很灵活，对模型而言中间任一步的意外输出都可能让结果失真，且没有契约可验证。三是能力发现弱：模型要靠 `--help` 摸索，参数靠推断，“应该这样传”正是出错的来源。

四是授权模型的局限。CLI 继承的是当前进程的凭证，隐含“调用者就是本机用户”的假设。单用户没问题；一旦 Agent 代表多个用户、横跨多个租户操作，单凭据多用户、无租户隔离、无撤销机制、无审计轨迹的问题会逐一浮现。五是安全边界模糊：给了 shell 就给了任意命令执行能力，模型幻觉或提示词注入都可能触发破坏性操作，这在共享的云端环境里影响会被放大。

需要补充的是，CLI 的多数短板可以被设计弥补，方向是“为 Agent 重新设计 CLI”：默认输出 JSON 而非人类表格，提供非交互与幂等选项，错误信息用结构化编码并给出可操作的修复提示，帮助文本写得像给模型看的说明书。飞书、钉钉、企微等厂商的新 CLI 基本都朝这个方向走，并且普遍附带 Skill 文档，把“有哪些命令、参数怎么传、什么场景怎么组合”预先写清楚。关于 Skill 的作用，第九节会展开。

## 七、MCP 的主场

一旦 Agent 开始代表他人行动，或者能力需要被多个客户端复用，MCP 的价值会迅速上升，超过它的 token 成本。这一节讲它赢在哪，代价是什么。

### 7.1 MCP 赢在哪

一是能力发现与契约。模型在运行时通过协议拿到结构化的能力清单，参数格式明确，不必靠摸索。对模型陌生的工具，这份清单是可靠的兜底。

二是授权、审计与身份。MCP 的授权规范把 OAuth、按用户授权、可撤销、租户隔离放在协议层，配合服务端审计日志，能支撑“Agent 代表客户操作跨系统数据”这类产品形态。对 CLI 的凭证继承模型，要做到同等程度的治理需要自己重造大量授权基础设施。

三是显式工具边界。模型只能调用已声明并经过批准的工具，无法像 shell 那样执行任意命令，这让企业环境下的安全评估更可控。

四是跨客户端复用的标准化基础。一个 server 可以被多个支持 MCP 的宿主接入，生态分发的路径也依赖这一点。五是它填补了 CLI 完全够不到的环境：没有 shell 的浏览器内 Agent、企业沙箱、嵌入式场景，CLI 路线根本不存在，MCP 是少数可行方案之一。

### 7.2 MCP 的代价

一是 schema 开销，第五节已经量化。二是运维负担：本地部署要养常驻进程、管理生命周期、处理跨进程调试，比“装个命令就能用”重。三是规范仍在演进，做 MCP 服务要持续跟进版本与各宿主差异。四是在“用户就是我自己、只有我一个客户端”的场景里，它是明显的过度设计——为不存在的问题支付协议复杂度。

需要提醒的是，上述短板有相当一部分来自实现而非协议。schema 膨胀可以靠过滤与缓存缓解，本地运维可以靠托管服务消除，模型熟悉度会随时间与文档质量提升。用一句话概括两派的分歧：CLI 的优点是效率，MCP 的优点是边界；效率派站在前者，治理派站在后者，谁都没有说错，只是各自看到的场景不同。

## 八、厂商的实际做法：两头下注

纸上争论归争论，真实产品给出了更统一的答案。截至 2026 年中，有规模、多用户、多入口的厂商普遍同时提供 CLI 与 MCP 两种形态，差别只在于分工方式。图 4 列了几家有代表性的产品。

![图 4 主要厂商同时提供 CLI 与 MCP 的情况](/blog/blog-resources/cli-vs-mcp/fig-vendor-table.svg)

*图 4 主要厂商同时提供 CLI 与 MCP 的情况。共同点是官方 CLI 几乎都配套官方 Skill，MCP 面向图形宿主与平台生态。*

先看飞书。飞书提供 Lark CLI 与官方 OpenAPI MCP，两者都由官方维护，定位互补而非主次。Lark CLI 有 200 多条命令、26 个 Skill，覆盖 18 个业务域，默认输出 JSON，面向“以个人身份操作全量业务”；OpenAPI MCP 默认只暴露约 20 个高频工具，底层可调度 1270 多个接口，需要按需切片加载以避免撑爆上下文。决定用哪个的边界大致有四条：身份（CLI 走个人 OAuth，MCP 以应用权限为主）、是否常驻（CLI 无需常驻进程，MCP 需要服务常驻）、格式保真（CLI 读取文档能保留完整富文本结构，MCP 目前只能拿纯文本）、事件与状态（以机器人身份常驻后台时 MCP 更合适）。

值得注意一个反直觉的细节：很多人以为“把完整文档喂给模型”是 MCP 的强项，实际在飞书这个例子里相反。文档有 40 多种块类型，CLI 能保留图片、流程图、代码块等完整结构，MCP 读文档会丢掉格式只剩纯文本。也就是说，“富内容读取”这一项，CLI 反而更强。

再看 Notion。Notion 提供托管的 MCP（22 个工具，集中在搜索、检索与页面数据读写，对应普通用户的高频操作）和面向开发者的 ntn CLI（把 Notion API 原样搬进终端，可上传图片与文件，配套 notion-cli Skill）。两条路径的分工更像是按用户画像：托管 MCP 服务没有本机 shell 的网页端用户，ntn CLI 服务专业开发者与 coding agent。

钉钉和企业微信的 CLI 则呈现出另一个有趣的结构：它们的 CLI 外壳内部跑的是 MCP 客户端逻辑，从服务端拉取工具注册表、做能力发现、经 JSON-RPC 执行。也就是说，在真实工程里，“执行层用 CLI、连接层用 MCP”的融合已经发生，争论的双方在实现层面并不互斥。

对普通产品团队的启示可以归纳为四点。业务操作面越广，越需要用 CLI 承接长尾操作，让 MCP 只保留精简的高频工具，为上下文减压。目标 Agent 分布在哪里是硬约束：用户多在本地终端 Agent，CLI 才能落地；多在网页端与平台内，MCP 更合适。给新 CLI 补多少“说明书”（Skill、规范 help、结构化错误码）直接决定它好不好用，这部分投入省不掉。不要把 CLI 与 MCP 分成先后主次，而是明确各自承接什么场景。

## 九、争论的真相：分界在哪

把前几节的结论放到一起，可以看清楚争论为什么持续存在，以及严肃的讨论最终收敛到哪里。

### 9.1 观点光谱

CLI 与 MCP 的立场大致可以分成四派。CLI-first 派认为命令行是模型的母语，MCP 对日常工具调用是多余的抽象，代表是若干英文开发者社群与个人实践。CLI 主导派认为 CLI 会成为主流、MCP 退守企业高安全场景，代表是不少中文综述。分层派认为两者根本不在同一层，应当组合，底层执行走 CLI，面向模型的暴露层按需包 MCP。治理派承认 CLI 便宜可靠的数据，但坚持当 Agent 代表客户、员工行动时，协议级的授权与审计不可替代。四派各执一词，但认真读完会发现，多数结论的差异来自适用范围的假设不同，而非事实层面的冲突。

### 9.2 三条分界线

把各派的判断标准放在一起，反复出现的分界线只有三条。

第一，Agent 为谁做事。代表开发者本人操作本机，CLI 足够；代表客户、员工或租户跨系统操作，需要协议级的授权边界。这是治理派与效率派分歧的根源，也是最硬的一条。

第二，目标环境有没有 shell，以及任务形态是否确定。能跑 shell、任务可脚本化，CLI 的组合优势才能兑现；没有 shell 的网页端、嵌入式环境，CLI 直接出局。这条决定了 CLI 在哪些场景根本不在候选名单里。

第三，是否要跨客户端复用与对外分发。CLI 是去中心化分发，渠道在自己手里；MCP 是平台化分发，可能借平台获得被发现的机会，但入口拥挤、质量参差，“支持 MCP”不等于获得流量，也不等于各宿主体验一致。

### 9.3 被多数文章低估的变量：Skill 层

前面反复出现一个词：Skill。它值得单独讨论，因为它是这场争论里常被漏掉、却可能改变结论的变量。

Skill 是一份预先写好的说明文档，通常以 SKILL.md 的形式存在，告诉模型某个任务怎么做：用什么工具、按什么顺序、边界情况如何处理、什么时候该停下来问人。它不属于 CLI 或 MCP 的任何一个层级，而是更上层的抽象——可以指导模型调用 MCP 工具，也可以指导它调用 CLI 命令，甚至两者混用。

Skill 的作用可以从两个方向看。对 CLI，Skill 补的是探索成本：裸 CLI 下模型要靠 `--help` 反复摸索，Skill 把这些信息预先写清楚，省去盲目试探。对 MCP，Skill 补的是初始化负担：它作为调度提示，告诉模型“做这类事情时优先用这几个工具”，把实际进入上下文的工具集收窄，从而降低 schema 常驻的开销。飞书 CLI 内置 26 个 Skill、钉钉 CLI 也有同样设计，本质上都在做这一层。

因此更准确的说法是：不管执行层选 CLI 还是 MCP，只要为 Agent 提供一份及时可靠的 Skill 说明书，首次调用的 token 消耗与出错率都能被压下去。反过来，没有这层，裸 CLI 的探索成本与裸 MCP 的 schema 开销都会被放大。这里可以顺带回答一个常见的争论点：CLI 单靠命令并没有真正“掀翻”MCP，真正改变结果的是“命令行加一层知识文件”的组合。

### 9.4 给实践者的判断顺序

落到具体选型，判断顺序比立场重要。先看目标 Agent 能否跑 shell，不能则 CLI 出局。再确认自己的能力是否有成熟官方 CLI 且模型熟悉，没有则 MCP 更有兜底。然后问三个问题：要不要跨客户端复用，Agent 代表谁，token 是否敏感。最后回到产品自身：鉴权、权限、审计是否就绪，决定能开放多少；业务面宽窄，决定长尾操作放 CLI 还是 MCP。这套顺序可以画成一张决策图，见图 5。

## 十、展望

未来的走向可以从两个协议自身的演进和整个技术栈的形态两个层面看。

CLI 一侧的演进方向是“为 Agent 重新设计”成为标准：默认结构化输出、非交互、幂等、明确退出码，帮助文本写得像说明书。更值得注意的是一类聚合工具的出现，它把若干现有 CLI 收进同一个命令面，甚至把没有 CLI 的网站与应用反向工程成命令。这类工具的共同特征是输出格式与错误码都按机器可解析设计，同时仍可被人类直接使用。“人机同用”从口号变成可验证的设计约束。

MCP 一侧，2026-07-28 规范做了规模最大的一次修订，方向与第五节指出的批评一一对应。协议改为无状态核心，服务可以部署在普通 HTTP 基础设施上做水平扩展；schema 与列表结果支持缓存时长，直接回应“烧 token”的批评；Extensions 框架与 MCP Apps 把能力扩展从规范主线程里拆出来，工具不再只返回数据，还能在宿主里渲染可交互界面；授权规范向 OAuth 与 OIDC 的实际部署方式靠拢；配套的废弃政策保证未来演进不必反复破坏既有实现。这些变化说明，MCP 正在把自己重新定位成一个可运行在通用基础设施上的标准契约层，而不是贴在某一种客户端上的私有协议。

再往上一层看，整个连接栈的形态也在收敛。图 6 展示一个被越来越多产品采用的分层结构：Skill 负责知识，即告诉模型怎么做；CLI 负责本地执行，即高效地跑命令；MCP 负责远程连接与治理；Agent 之间的协作由 A2A 一类的协议承担。每一层只解决自己擅长的问题。分层论不是折中主义的和稀泥，它符合工程上对稳定接口的偏好：本地高频的执行不需要协议开销，远程低频的治理需要集中。

![图 6 Agent 连接栈的分层](/blog/blog-resources/cli-vs-mcp/fig-stack-layers.svg)

*图 6 Agent 连接栈的分层。Skill 在上层组织知识，CLI 与 MCP 分别承担本地执行与远程连接，层与层之间可以组合。*

一个更具判断性的看法来自 S06 那类文章：随着 Skill 层成熟，“MCP 还是 CLI”这个问题本身可能变得不重要。用户和 Agent 只关心任务是否完成，至于底层执行走的是协议还是命令，会逐渐成为一个实现细节。真正值得投入的是把高价值、高频的场景封装成 Skill 友好的能力包，并保证产品具备可检查、可追责、可优化的过程。

如果把视角再放远一点，这场争论可以看作是“中间软件层为 Agent 重构”的一个切面。功能层面的壁垒在瓦解：以前需要几周开发的功能，如今借助 AI 工具几个小时就能复制。真正难以替代的壁垒是跨客户、跨时间沉淀下来的领域上下文，即业务记录、用户偏好、决策模式与流程规则。对 SaaS 产品而言，开放给 Agent 的本质不是开放功能接口，而是开放上下文接口。这个判断决定了产品暴露什么、暴露多少，也决定了它在 Agent 时代的生态位。CLI 与 MCP 之争，最终会退到这个问题背后。

## 十一、结论

回到开头的场景。给 Agent 一双什么样的手，取决于这双手要做什么活。CLI 像跑鞋，在本地、单人、高频的平路上轻快直接；MCP 像工装靴，在跨系统、多租户、需要审计与授权管控的工地上更稳当。二者不是替代关系，而是针对不同场景的两套接口。

本文的结论可以压缩成三句话。第一，CLI 与 MCP 不在同一层级，比较时要带上前提：传统 CLI 的优势不会自动落在新做的 Agent 原生 CLI 上。第二，真实产品的答案是组合与分工，而不是二选一：有规模的厂商几乎都同时提供两种形态，区别只在按身份、场景还是用户画像分工。第三，随着 Skill 这类上层抽象成熟，“用哪个协议”这个问题的重要性在下降，讨论的重心会从接口选型转向能力如何被组织、治理与复用。

对实践者，一个稳妥的起点是：先用 CLI 加 Skill 把能力跑通，尤其是当产品本来就有成熟命令工具的时候；等到出现多个客户端要复用、Agent 要代表客户操作、或者远程治理成为刚需，再补上 MCP。收窄好的业务逻辑，无论最后包成命令还是协议，都能共用，这一层不会白做。
