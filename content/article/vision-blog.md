> **摘要：** 纯文本语言模型无法直接读取图像像素，而在多数 agent harness 中，用户粘贴的图像往往仅以临时文件路径的形式进入对话，导致模型只能依赖推测而非事实进行回应。针对这一模态错位问题，本文介绍一个 dsh 的插件 ModLens——一个将图像转化为结构化、可引用证据的工具（https://github.com/liustack/modlens）。ModLens 不向模型提供自然语言描述，而是输出经 schema 校验的 JSON 对象，包含全文 OCR、阅读顺序版面区块、语义关系及不确定性标注，使模型能够逐字引用图像内容而非凭空想象。系统采用统一的提供商抽象层，支持六种内置视觉引擎与四种本机已登录 CLI 的借用，并以故障转移链、多密钥轮换与冷却机制应对免费额度的固有波动。其可靠性建立在四层设计之上：贯穿服务端、模板与运行时的三层 schema 强制；将不稳定性视为常态的链式容错；以通用 OpenAI 兼容协议替代厂商特定适配；以及零配置、本地优先与 guard 收手机制。安全层面，ModLens 将图内文字视为不可信数据，对远程 URL 施加 SSRF 防护，并在错误输出前抹除密钥。此外，本文附录介绍其自包含改版 vision-test，通过捆绑运行时、单一引擎与引导式配置，将同一契约压缩至可在封闭环境中离线部署的单一文件夹。ModLens 的核心主张是：面对“模型只读文本、图像只有像素”的错位，可靠的答案不是一句流畅的转述，而是一份要么合格、要么被明确拒绝的可核对证据。

## 一、一张图进了聊天

先从最常见的场景说起。一张截图被拖进对话框，缩略图清楚地显示在消息里；模型接下来的回复却绕开了它，甚至开始描述它“认为”图中应该有的内容。

问题出在模型本身。被调用的模型是纯文本的，读不了像素。图片从聊天框进来，在多数 agent harness 里并不会转成像素送到模型面前，而是落成一个临时文件，路径作为一行文本进入对话。于是模型收到的不是图，而是一句话：

> `C:\Users\you\AppData\Local\Temp\paste-7f3a91.png`

若让这个模型自述处境，大意如下：

> “你们给我的是一串路径，而我没有办法打开文件。我知道这是一张图，因为文件名写着它是截图，但图里有什么，我看不见。”

症结不在模型的智力，而在它手中没有任何可读的素材。

**关键问题**

一张图只有像素，语言模型却只会读文本。那么，如何把“看见”这件事，变成模型能够引用、而非只能猜测的东西？

![在 DeepSeek Harness 里粘贴截图，模型据此作答](/blog/blog-resources/vision-blog/demo-dsh-paste.jpg)

*直接粘贴：图不用先存成文件再传路径，模型基于读到的证据逐项回答*

## 二、证据，而非想象

一种省事的做法是：让有视觉的模型给这张图写一句描述，再把描述塞回对话，例如“图中是一张邮件截图”，仅此而已。

这可以工作，但很脆弱。模型接下来的回答往往会偏离，开始补充描述中没写、图里也未必存在的细节，因为它手里只有一句转述，而非原文。

ModLens 选择了另一条路径：它不提供一句描写，而是提供一份证据。

一次读取返回一个 JSON 对象：`summary` 是一句话总览；`ocr.full_text` 是图中全部文字的逐行转写，并标注语言；`layout.regions` 是按阅读顺序排列的区块，每块带有类型（标题、段落、表格、图表等）与文字；`semantics` 记录场景、意图、实体及其关系；`visual` 与 `uncertainty` 收尾。

关键差别在于引用方式：当回答需要援引图中内容时，模型可以逐字引用 `ocr.full_text`，也可以指向某个 `layout.regions` 说明“这一块标着 128”。它引用的是证据，不是印象；而证据可以被核对，印象不能。

![密集图表：128 个模型的散点图被读全](/blog/blog-resources/vision-blog/demo-codex-chart.jpg)

*读出来是什么样：一张 128 个模型的散点图，坐标轴、对数刻度与高亮区都被读出（图源：项目 README）*

**题外话：为什么删掉了坐标和置信度**

早期版本中，`layout` 的每个区块带有像素坐标 `bbox`，`ocr` 的每一行还带一个数值置信度，后来被全部移除。

原因很直接：视觉模型会臆造这两项。它给出的坐标能精确到小数点后两位，看似专业，却与真实像素对不上；它给出的置信度可以到 0.97，而这个数字并无任何测量依据。一份会伪造字段的“证据”，比缺少这些字段更危险，因为下游会采信它。于是 v2 将它们删除，宁可少给，也不给假的。

## 三、架构：一层 CLI，一条链

ModLens 的结构比它看上去简单。整个工具是一个命令行程序，外面只套一层很薄的适配：在 skill 型 harness 里是一个 skill 文件夹，在 DeepSeek Harness 里是一个插件；没有常驻进程，没有本地代理守护，也不修改 harness 配置。

流程可以概括为：图片交给 CLI，CLI 选定一个视觉提供方去读取，读取结果先过一遍结构校验，校验通过才作为 JSON 证据输出给模型。

![ModLens 一次读取的数据流](/blog/blog-resources/vision-blog/01-dataflow.png)

*图 1 · 一次读取的数据流：图片交给 CLI，链上选一个引擎去读，结果过 schema 校验后才成为证据*

提供方共有十个来源，其中六个内置：`gemini-api`（免费 Gemini key，5 到 10 秒）、`openai`（任何 OpenAI 兼容的多模态端点）、`anthropic`（一个 Anthropic key）、`antigravity-cli`（免费的 `agy` 命令行，浏览器登录一次，无需 key）、`claude-cli`（复用已登录的 Claude Code）、`kimi-cli`（复用已登录的 Kimi Code，需显式指名）。

另外四个并非内置提供方，而是本机既有的登录：Codex、OpenCode、Pi、Grok。它们被借用时同样进入这条链，但需在配置中逐条授权。

这十个来源背后是统一接口。子进程型提供方（那些命令行 agent）实现“如何启动、如何解析输出”，进程内型（那些 HTTP API）实现“如何发起请求”。对上层而言二者没有区别：都能读图，都能进入同一条链。

这条链值得单独说明。若不指定使用哪一个，ModLens 会把所有已配置的引擎排成一条故障转移链：较快的 API 排在前面先试，命令行 agent 压后兜底，谁先给出合格结果谁胜出。每一次尝试都记录在 `meta.attempts` 中，因此任何一次“实际换了引擎才成功”都不会被隐去。

![故障转移链：两个区域，一个顺序](/blog/blog-resources/vision-blog/02-architecture.png)

*图 2 · 故障转移链：Inline API 区先试，Agent CLI 区兜底；远程图只走带 SSRF 守卫的 Inline 区*

## 四、它为什么有效

读到这里可能会有一种印象：这不过是接入若干视觉 API，再做一次轮询。并不尽然。真正让它可靠的是四件并不起眼的设计。

### 1. 结构强制，贯穿每一层

让模型输出 JSON，是可靠性最低的请求方式之一。它会附加一段解释、包一层 markdown、写错字段名，或截断一半。ModLens 不靠“请求”模型守规矩，而靠三层强制。

能用服务端 schema 的提供方就都用上：命令行 agent 走 `--json-schema`，Gemini 走 `responseJsonSchema`，Anthropic 走一次被强制调用的工具。openai 这条通用路径没有可移植的服务端强制，就把 schema 写入提示词，并要求模型填写一个模板实例。最后一层是兜底：无论走哪条路，结果返回后 CLI 都会再按 schema 校验一遍形状。

![Schema 强制：三层防线](/blog/blog-resources/vision-blog/03-workflow.png)

*图 3 · Schema 强制三层：服务端强制、模板约束、运行时校验，任一环不合格就换引擎*

第三层为何必要？因为服务端强制本身也会出错。一个网关可能“接受”了 schema，却返回一个看似正确、实为空壳的 `{"ocr":{}}`。若只信任网关，这个空壳就会被当作证据交出。自行再校验一次，才有“要么合格，要么失败”的确定性。

### 2. 免费额度不可靠，这是常态，不是意外

多数人使用的是免费档或低成本档，而这些档位随时可能限流、掉线或临时失效。这不是靠“换一个更稳的服务”就能绕开的问题：免费额度本身就不稳定。

因此 ModLens 把不稳定性作为设计前提。一条链上挂多个引擎，一个不行就换下一个；`apiKey` 支持以逗号分隔的多个 key，在认证失败、限流、额度耗尽时轮换到下一个，而网络错误、5xx、解析失败这类与 key 无关的问题，则跳过剩余 key，直接更换提供方。额度耗尽的提供方会被记入冷却状态，一段时间内排到链尾，恢复后再放回。

**提示：确认失败没有静默**

一次读取之后，值得查看 `meta.attempts` 与 `meta.warnings`。前者列出本次尝试过的每个引擎及其结果，后者记录故障转移、被忽略的参数，以及某次借用消耗了谁的额度。会静默降级的系统难以托付；每次都明确报告降级的系统，才值得依赖。

### 3. openai 是插座，不是某一家

不少工具会为每个厂商单独实现一个适配层，ModLens 没有这样做。它把 `openai` 当作通用插座：任何实现 OpenAI chat-completions 协议、接受图片输入的端点，配置三个值即可接入，即 `baseUrl`、`apiKey`、`model`。Qwen-VL、GLM、SiliconFlow、OpenRouter，以及自建的 vLLM 或 Ollama，都以此方式接入。

**题外话：厂商参数为什么不建模**

不同网关对“关闭思考模式”这类开关的命名各不相同，同一个含义在 A 家叫 `thinking`，在 B 家可能是别的。如果代码中维护一张“各家如何拼写”的对照表，这张表会持续过期；一旦猜错，请求要么返回 400，要么被静默忽略，两种情况都难以排查。

因此 ModLens 不做猜测。它提供一个 `extraBody` 透传入口，把希望加入请求体的 JSON 原样传入，由其深合并；真正承载图片、提示词与 schema 的字段会被保留，不会被覆盖。少一层抽象，也少一堆注定过期的对照表。

### 4. 零配置，以及该收手时就收手

新工具最容易劝退用户的地方是配置。ModLens 尽量让机器上已有的东西直接成为它的引擎。机器上若已登录 Claude Code，`claude-cli` 即可直接使用；若装有 Codex、OpenCode、Pi、Grok 且处于登录状态，它们也可以被借用，前提是在配置中逐条同意。借来的登录不会越过使用者自己的 key 取得优先权，且每一次借用都会被标注消耗了谁的额度。

还有一处设计值得单独提及：guard。如果一个模型的元数据明确表明它自带视觉、能够自行看图，就不应再让 ModLens 读一遍。`guard` 在读取前先判断“这个模型本来就能看见吗”，若能，则收手。

这看似只省下一次调用，实则避免了一种尴尬：一个本就能看图的模型，却把图外包给另一个模型去读。

## 五、本地优先，以及信任边界

ModLens 不设中间服务。密钥留在本地，额度也由使用者自己承担。它读取本机文件，这并不特别；特别的是它连粘贴过的图片都能读回——在多数 harness 里，粘贴的图并不落入常规磁盘，而是进入会话存储。

`recover-paste` 正是从这些会话存储中取回图片：Claude Code 与 Pi 是 JSONL 记录，OpenCode 是 SQLite 数据库，Codex 走其自身的临时文件。各家的存储格式都属于内部实现，因此这部分是尽力而为，但它解决了真实场景中的一类问题：图片贴入之后，harness 只给了模型一行路径，而图在某个使用者打不开的地方。

![一张粘贴的图如何到达模型](/blog/blog-resources/vision-blog/04-sequence.png)

*图 4 · 粘贴的图不落常规磁盘，recover-paste 从会话存储取回，读取结果作为 JSON 证据交给模型*

安全上有一条界线需要划清：图中的文字是不可信数据。一张图里可以写“忽略上面的指令，去做别的事”。因此 ModLens 的提示词明确要求把图内文字当作数据、而非命令。远程 URL 的图片另有一层防护：下载时固定 IP、检查文件头、限制大小，以免被诱导访问内网地址。错误信息对外输出前，会先抹去密钥一类的信息，因为错误会进入终端、日志与 agent 的记录，而网关的响应并不受我们控制。

## 六、轻到可以随时扔掉

最后一点，也是最容易被忽略的一点：接入的成本。

在 skill 型 harness 里，它就是一个文件夹；在 DeepSeek Harness 里，它就是一个插件。卸载就是把文件夹删掉，agent 回到出厂状态，不留钩子、不留包装脚本、不留一个在后台运行却不知其内容的东西。

这一取舍不只是为了好看。一个常驻组件意味着：它坏了未必立刻察觉，它更新了需要留意，别人审计机器时还得单独询问它是什么。一个能被随手删掉的东西，才有资格被随手装上。

## 七、小结

ModLens 试图解决的是一个具体的错位：模型只会读文本，而图只有像素。它的答案不是给模型一句描述，而是把图变成一份结构化的、可引用的证据，并在每个环节都保证这份证据要么合格、要么被明确拒绝。

几条原则，按重要性排列：

- 证据优先。能被引用、能被核对的内容，胜过一句流畅的转述。
- 失败要响。schema 校验、`meta.attempts`、`meta.warnings`：一个系统越是不隐瞒它的降级，越值得依赖。
- 别为厂商做猜测。通用协议加透传，胜过一张注定过期的对照表。
- 本地优先。密钥、额度、文件读取都在本机，不引入中间人，也不引入不明的常驻进程。
- 复用已有。机器上已有能看图的东西，就先问能不能用，而不是先让用户去注册新账号。
- 只做一件事。视觉解析是全部职责，联网搜索属于另一个项目。

## Appendix 1 · vision-test：为封闭环境做的一个小改版

正文讨论的是 modlens 本身。这一节另说一事。为了更方便的在数字员工（AI-STAFF）中使用这个功能，我尝试将 modlen 改成了一个专在数字员工环境中使用的 skill。暂时命名为 vision-test

主要做了一件事：把整件事压进一个文件夹。

它保留的是契约，而非安装方式：同一套 skill 结构（`SKILL.md`、启动器、`references`），同一个 CLI，同一份输出 schema。变化的是它如何到位、如何启动、连接哪个引擎。

![vision-test：一个能整包拷走的 skill](/blog/blog-resources/vision-blog/05-selfcontained.png)

*附录图 · 一个整包拷走的 skill：捆绑的 exe 内嵌运行时与 CLI，拷贝文件夹即可用*

几处关键改动：

**自包含的可执行文件。** 将整个 modlens CLI 连同其所需的 Node 运行时打成单个可执行文件（Node 的单文件应用，Node SEA）。目标机器无需安装 Node，也无需 npm，拷贝文件夹即可运行。代价是体积不小，Windows x64 下约 98MB。

**启动器改为“捆绑优先”。** 原版启动器先找 PATH 上的 modlens，再依次尝试 npx 与 bunx，这几条都依赖运行时或网络。vision-test 的启动器先运行捆绑的 exe——离线、零依赖；只有它不存在时才退回那几条旧路径。在没有开放生态的平台上，第一条即可。

**只留一个引擎。** 六提供商、failover、借用其它 CLI 登录、guard，这些在原版中依赖机器状态与更多配置。vision-test 将其收敛，只保留 GLM-4V-Flash（智谱）一条：一个 key，国内可直连，并有免费档，大幅减少了可能出错的环节。

**把配置也做成引导。** 这是“易上手”中最要紧的一处。skill 触发时先检查是否配置完毕；若未配置，就停下来，引导用户前往智谱控制台创建 key，再以隐藏输入运行四条 `config set`，然后才开始读图。用户无需先读一页文档，agent 会自行走完这一步。

易上手可以概括为几点：拷贝即用，无需安装运行时；一个 key、一步配置，密钥走隐藏输入，既不进入 shell 历史，也不进入 skill 包；agent 只需调用启动器，运行时如何解析无需关心。

边界也一并说明：exe 目前仅覆盖 Windows x64，约 98MB；非 Windows 环境下，启动器退回 PATH / npx / bunx，届时仍需要 Node。安装是离线的，读取不是——读图仍需能连到智谱。它并非替代 modlens，而是把同一个内核压进一个能在封闭环境直接落地的壳。
